# Architecture

This fork uses a direct JSON file architecture. The retained CLI does not require SQLite, a daemon, a sync branch, or a monolithic JSONL source of truth.

## Layers

```text
CLI command
  |
  v
FileStorage
  |
  v
.task-ledger/issues/**/issue.json
  |
  v
Git
```

`FileStorage` loads all issue files into a command-local index, executes the requested operation, and writes touched files back to disk. The temporary maps are scoped to one CLI process; disk remains the source of truth.

## Storage

The canonical repository data lives under `.task-ledger/issues`:

```text
.task-ledger/issues/
  fr-a3f2dd/
    issue.json
    epics/
      ep-91c0af/
        issue.json
        tasks/
          tk-b841aa/
            issue.json
```

Each file is stable formatted JSON with `schema_version: 1`. Labels, comments, dependencies, scheduling fields, close/delete metadata, and hierarchy pointers are embedded in the issue file.

## Read Path

For a read command such as `tl ready`:

1. Discover every `.task-ledger/issues/**/issue.json`.
2. Parse each file into the runtime issue model.
3. Build temporary maps for IDs, dependencies, labels, and comments.
4. Run the query against the command-local index.
5. Print text or JSON output.

For the target scale of this fork, usually hundreds and occasionally around a thousand issues per repository, loading files per command is simpler and fast enough.

## Write Path

For a write command such as `tl update`:

1. Load all issue files.
2. Acquire the file-backend write lock.
3. Reload all issue files after the lock is acquired so concurrent writers do not apply stale state.
4. Snapshot touched files for rollback.
5. Apply the mutation to the command-local index.
6. Write affected `issue.json` files atomically.
7. Move files if hierarchy changed.
8. Restore the snapshot if any step fails.

The backend uses atomic temp-file replacement for writes and prunes empty directories after moves. Soft-deleted issues remain as tombstone files so audit metadata is preserved.

## IDs

IDs are generated by issue type:

| Type | Prefix |
| --- | --- |
| `feature_request`, `feature`, `FR` | `fr-` |
| `epic` | `ep-` |
| `task` | `tk-` |
| `bug` | `bug-` |
| `chore` | `ch-` |

The suffix is random, so parallel agents can create work without sequential ID coordination.

## Hierarchy

Hierarchy is represented both by file path and explicit fields:

- Feature requests are top-level directories under `.task-ledger/issues`.
- Epics are stored under `<fr>/epics/<epic>/issue.json`.
- Tasks, bugs, and chores are stored under `<fr>/epics/<epic>/tasks/<id>/issue.json`.
- `parent`, `feature_request`, and `epic` fields make the relationship easy to query from a single file.
- A `parent-child` dependency is also retained for compatibility with graph commands.

## Dependencies

Dependencies are embedded in the dependent issue file:

- `deps` is a short list of blocking IDs.
- `dependencies` stores full dependency records, including dependency type.

This keeps a dependency update local to the issue being changed in the common case.

`external_ref` is unique when present. The loader, create/update paths, batch create, and import path reject duplicates instead of choosing an arbitrary issue.

## Comments and Audit Metadata

Comments are stored inline in `comments`. Actor metadata is written from `--actor`, `TL_ACTOR`, git user name, or the current user. Close/delete metadata is stored on the issue itself. `tl delete` creates a tombstone instead of removing the issue file.

This fork does not require a separate events table. If richer audit events are added later, they should be added as explicit JSON fields or per-issue event arrays while keeping the issue file self-contained.

## Legacy Product Code Removed

The legacy SQLite, daemon/RPC, import/export loop, sync-branch, Linear, formula, molecule, routing, and compact packages have been removed from the retained Go package graph. The file backend owns the command-local issue index it rebuilds from disk for each CLI process.

The supported user-facing command allowlist is implemented in `cmd/tl/zz_file_backend_commands.go`.

## Testing

